# Architecture

LedgerGuard reconciles a bank statement against an internal ledger through six layers (L0-L5)
plus one feedback loop (D1). Every layer except L2 is deterministic code with no model in the
loop -- see `docs/adr/001-single-ai-component.md` for why that's a deliberate constraint, not an
accident.

![LedgerGuard architecture diagram](architecture.png)

(Source: `docs/generate_architecture_diagram.py`, run once and committed like any other design
illustration -- unlike the benchmark charts in `eval/output/`, which are regenerated by `make

## The layers

- **L0 — Normalization** (`ledgerguard/l0_normalize/`): paise integers, UTC timestamps,
  narration cleanup. Never makes a matching decision, never touches the network.
- **L1 — Deterministic Matcher** (`ledgerguard/l1_deterministic/`): exact net-amount + a [2,4]-day
  settlement-tolerance band, plus a bounded subset-sum search (capped by `MAX_GROUP_SIZE` and
  `MAX_SEARCH_NODES`, so a pathological candidate pool escalates rather than hangs) for
  split-settlements. No narration signal gates this layer at all -- narration only ever informs
  L2/D1's plausibility scoring.
- **L2 — LLM Triage** (`ledgerguard/l2_llm_triage/`): the **only** LLM call site, and it only ever
  sees the residual L1 could not resolve (`tests/test_l2_never_sees_resolved.py` asserts this).
  Receives one bounded candidate set, returns a schema-validated `{candidate_id | null,
  confidence, evidence[]}`. Served by a free rapidfuzz fallback in every session so far -- no
  environment this project has run in has had live Anthropic credentials (see
  `REAL_VS_SIMULATED.md`).
- **L3 — Calibrated Gate** (`ledgerguard/l3_calibrate_gate/`): a logistic-regression calibrator
  (fit on validation only) turns raw confidence into a calibrated probability; a cost-model-driven
  threshold (minimizing expected ₹ cost, not maximizing accuracy) decides AUTO_POST vs. ESCALATE.
  Escalated cases rank into an exception queue by rupees at risk.
- **L4 — Anomaly Detection** (`ledgerguard/l4_anomaly/`): has veto power over L1 and L3 -- a flag
  here always beats a confident match. Four detectors: duplicate UTR, genuine double-settlement,
  missing settlement, fee/tax contract violation.
- **L5 — Bounded Executor** (`ledgerguard/l5_executor/`): the authority policy (`gate action ==
  AUTO_POST AND amount <= limit AND no anomaly flag`) and the idempotency key (`SHA-256(batch_id
  + bank_line_id)`, enforced by a DB-level `UNIQUE` constraint) that makes a rerun of the same
  batch byte-identical on `audit.jsonl` and add zero duplicate ledger rows
  (`tests/test_idempotency.py`).
- **D1 — Rule Learning** (`ledgerguard/d1_rule_learning/`): a human-resolved exception becomes a
  candidate rule (narration scope + widened tolerance), replayed against train+validation history,
  and promoted into L1's own rule chain only if it hits at least 3 times with zero false
  positives. This is the loop that makes the LLM's own workload shrink over time (`eval/rule_learning.py`,
  Phase 8's measured result: invocation rate 17.1% → 15.0% → 11.2% across 3 batches).

A parallel, separate path — **D2 — Red Team** (`data/redteam.py`, `eval/redteam_eval.py`) —
attacks the shipped pipeline with adversarial cases and reports a measured survival rate, kept
fully out of the holdout split so it never contaminates the headline ablation numbers below.

## Design invariants (asserted directly in tests, not just documented)

- **L2 never sees a record L1 already resolved.** If it did, the "the model's footprint should
  shrink over time" claim would collapse into "the model does everything, sometimes redundantly."
- **An anomaly flag always beats a confident match.** L4 runs after L1/L3 and can force ESCALATE
  or FLAG_ANOMALY regardless of how confidently anything upstream resolved a bank line.
- **A rerun of the same batch is byte-identical and never double-posts.** No wall clock anywhere
  in the pipeline; `created_at` on every decision is the bank line's own `value_date`, not
  `datetime.now()`.
- **Built-ins always get first refusal.** D1's learned rules are appended to L1's registry *after*
  the hand-written rules, so a learned rule can only narrow what's already unresolved, never
  override a built-in's own confident answer.

## Why this shape, not a multi-agent pipeline

See `docs/adr/001-single-ai-component.md` for the full reasoning: one narrowly-scoped LLM call
site, justified only by a falsifiable, measured gap on holdout (`PREREGISTRATION.md`,
`benchmark/ablation.py`) -- not by a stylistic preference for minimalism, and not added to or
split further without an equivalent measured justification.
